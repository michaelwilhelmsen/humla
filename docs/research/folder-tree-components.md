# Folder tree rendering options for Humla's sidebar (#162)

## Sammendrag

- **kibo-ui's Tree is a shadcn-registry source port (`npx kibo-ui add tree`), not an npm install** — confirmed by direct inspection of `haydenbleasel/kibo`'s source: it depends on `motion` + `lucide-react`, uses a plain `cn()` helper (no CVA, no Radix), and its Tailwind classes are literally shadcn-token-named (`bg-accent/50`, `border-border`, `muted-foreground`) — every one would need remapping to Humla's own tokens.
- **The single biggest finding: kibo-ui's Tree has no ARIA roles, no arrow-key keyboard navigation, and no drag-and-drop in its source**, despite the docs page's "Keyboard navigation support" bullet — that bullet refers only to Ctrl/Cmd-click multi-select. It is visually a tree, not interactively one. Porting it buys animated expand/collapse and icons, and discharges none of #162's actual hard requirement (accessible keyboard reparenting).
- **`headless-tree` (lukasbach.com), the explicitly-declared successor to `react-complex-tree` by the same author**, is the strongest candidate found: fully headless, ships ordered drag-and-drop, typeahead, and — critically — auto-computes `aria-level`/`aria-setsize`/`aria-posinset`/`aria-expanded` per its own docs. Caveat: **Beta as of May 2026**, GA not yet confirmed.
- **Neither Radix, Base UI, nor Ariakit ship a tree primitive** — Base UI has an open unresolved feature request (`mui/base-ui#3327`). A hand-build on Radix is possible (`RovingFocusGroup` + `Collapsible` as building blocks) but means writing the entire ARIA/keyboard contract from scratch.
- **Virtualization is a non-issue at Humla's scale** (tens of folders) — don't let it influence the choice.

## 1. kibo-ui's Tree component

**What it actually is:** kibo-ui is *not* an npm package you `npm install`. It is a **shadcn/ui-style component registry** ("A custom registry of composable, accessible and open source shadcn/ui components", per its own GitHub description) maintained by Hayden Bleasel — repo `haydenbleasel/kibo` [SANNSYNLIG — confirmed via search snippets of the GitHub repo description; I did not open the raw source file for the tree component itself within budget]. Installation is via the registry CLI pattern:

```
npx kibo-ui add tree
```

— which follows exactly the shadcn `npx shadcn add <component>` mechanism (a registry JSON manifest that the CLI resolves and **writes the component's source files directly into your repo**, typically under `components/ui/`). This is confirmed by the docs page itself, which gives the `npx kibo-ui add tree` install command [DOK — https://www.kibo-ui.com/components/tree]. So: **it inlines source, it is a port target, not an npm dependency you can just add to `package.json`.**

**Dependencies (from the docs page + registry model):**
- Built explicitly "for use with shadcn/ui" — the kibo-ui docs and marketing copy state its components "use shadcn/ui CSS variables and are designed to work neatly with the existing primitives" [SANNSYNLIG — from search-result summary of kibo-ui's own positioning, not independently opened]. That means it assumes the shadcn token vocabulary (`--background`, `--primary`, `--muted-foreground`, `--border`, etc.) is already defined in the consuming app's CSS — the exact vocabulary Humla deliberately does not have.
- The docs page for Tree specifically credits **motion.dev** ("Powered by motion.dev") for the expand/collapse animation and **lucide.dev** for icons [DOK — page content via WebFetch of https://www.kibo-ui.com/components/tree]. Humla already uses `lucide-react`, so that part is a non-issue; `motion` (Framer Motion's successor) is not currently a Humla dependency and would be a new one.
- I could **not** confirm from the docs page alone whether the Tree component specifically wraps Radix, CVA, or `tailwind-merge`/`cn()` — the fetched page did not show the actual source/import block. kibo-ui's general pattern (like shadcn itself) is to use a shared `cn()` helper (clsx + tailwind-merge) across all its registry components, and several other kibo-ui components are known to wrap headless libraries under the hood ("wrap more complex logic from various headless libraries to provide a more seamless experience" per a third-party registry aggregator's description) [SANNSYNLIG]. Whether Tree specifically is built on a headless tree lib (e.g. it could be a thin styled wrapper the author wrote directly, not on top of react-arborist/etc.) is **[IKKE FUNNET — søkte etter "kibo-ui tree.tsx source" and the raw component file; only the rendered docs page and third-party summaries were reachable within budget]**.
- No CVA (`class-variance-authority`) usage was visible or confirmable from what was fetched; not enough evidence either way — recorded as a gap, not a finding.

**Headless or opinionated?** Opinionated. It ships pre-styled Tailwind classes tied to shadcn tokens, animated via motion.dev, with a "fully composable API for custom tree nodes" (i.e., you can swap the node renderer, but the shipped chrome — spacing, animation, hover states — is shadcn-flavoured) [DOK, page copy quoted above].

**Features out of the box** (quoted from the docs page):
> "Animated expand/collapse with configurable animations, Customizable node icons and labels, Single and multi-selection support, Optional tree lines for visual hierarchy, Keyboard navigation support (Ctrl/Cmd for multi-select), Fully composable API for custom tree nodes" [DOK — https://www.kibo-ui.com/components/tree]

- **Expand/collapse:** yes, animated.
- **Keyboard navigation:** yes, but the docs only mention **Ctrl/Cmd-for-multi-select** explicitly — no mention of arrow-key traversal, Left/Right to collapse/expand a node, Home/End, or typeahead. This is a meaningful gap against the full WAI-ARIA `tree` pattern (see §4).
- **Selection:** yes, single and multi.
- **Drag-and-drop reparenting:** **not listed as a feature anywhere on the page** — I looked for it specifically and it is absent from the feature bullet list. Treat this as "not supported out of the box" rather than confirmed-absent-forever, since I could not open the source to double check for an unlisted/undocumented DnD prop. **[IKKE FUNNET — søkte etter drag-and-drop/reparenting explicitly on the docs page; not mentioned]**.
- These capabilities are not described as separable/composable pieces (e.g. "use just the keyboard nav hook") — the registry model gives you the whole file; you then edit it yourself to strip parts you don't want, which is a normal part of the "port cost" below.

**Confirmed from the actual source** (`packages/tree/index.tsx` and `packages/tree/package.json` in `haydenbleasel/kibo`, fetched via raw.githubusercontent.com) [DOK — https://raw.githubusercontent.com/haydenbleasel/kibo/main/packages/tree/package.json and .../index.tsx]:

- **Runtime dependencies:** `motion` (^12.23.24, i.e. Framer Motion's successor package), `lucide-react` (^0.545.0), `react`/`react-dom` ^19.2.0, plus an internal workspace package `@repo/shadcn-ui`. **No `class-variance-authority`, no Radix package, no `tailwind-merge` as a direct dependency** (a `cn()` helper is imported from `@/lib/utils` and tailwind-merge is *likely* inside that shared helper, but it's not a dependency of the tree package itself).
- **Radix: absent.** The component is a plain React tree built from scratch on `<div>`/`<ul>`-equivalent markup with a Context provider for expand/select state — it does **not** sit on any Radix primitive. This matters for Humla: adopting it does not slot into the existing "everything anchored goes through the four Radix wrappers" convention; it would be a structurally different, parallel styling approach living next to them.
- **Keyboard navigation reality check: there is no arrow-key handling in the source at all.** No `ArrowLeft`/`ArrowRight`/`ArrowUp`/`ArrowDown`/`Home`/`End` key handling exists in `index.tsx`. The docs page's "Keyboard navigation support (Ctrl/Cmd for multi-select)" bullet refers only to holding Ctrl/Cmd while **clicking** to multi-select — not to arrow-key tree traversal. **This is the single most important finding of this report: kibo-ui's Tree does not implement any part of the WAI-ARIA `tree` keyboard pattern.** It is visually a tree; interactively it is a flat list of clickable rows with indentation and animated disclosure.
- **Drag-and-drop: confirmed absent from source**, not just undocumented — no `dnd-kit`, `react-dnd`, `draggable` attribute, `onDragStart`/`onDrop` handlers anywhere in the file.
- **Styling is directly shadcn-token-coupled in the Tailwind class strings themselves** — e.g. `hover:bg-accent/50`, `bg-accent/80`, `border-border`, `muted-foreground` appear as literal utility classes in the component markup. This is not a CSS-variable file you swap once; the token names are baked into `className` strings throughout the component and would need find-and-replace across every node-rendering branch.

## 2. Port cost if inlined via shadcn registry

Since kibo-ui's Tree is confirmed (§1) to be a single ~one-file component (`index.tsx`) with no Radix underneath, the port is smaller in raw line count than a typical shadcn table/data-grid port, but the coupling is **class-name-level, not variable-level**:

- Every `bg-accent`, `border-border`, `muted-foreground` etc. is a literal Tailwind utility class referencing shadcn's default token names, which Tailwind resolves against shadcn's CSS-variable definitions (`--accent`, `--border`, `--muted-foreground`) that **do not exist in Humla's `globals.css`**. Because Humla's own tokens are named differently (`--color-canvas`, `--color-accent`, `--color-surface-2`, `--color-pill-hover`, `--color-accent-text`, etc. — see project CLAUDE.md design-system section) and carry different semantics (e.g. Humla's `--color-accent` is gold and reserved for filled primary buttons, *not* a general hover-state background the way shadcn's `accent` token is used), a straight find-and-replace of token names is not safe — each usage has to be re-reasoned against Humla's actual vocabulary (probably `hover:bg-accent/50` → something like `.nd-meta.is-interactive`'s hover fill, `border-border` → a Humla border/divider token if Humla has one, `muted-foreground` → `--color-*-text` variants).
- The animation dependency (`motion`) is new to Humla's `package.json` — not currently used anywhere per the project's documented stack (Humla uses no animation library today beyond CSS transitions implied by the design-system utilities). Adding it is a real (if small) new runtime dependency purely for tree disclosure animation, which Humla could equally do with a CSS `max-height`/`grid-rows` transition or Tailwind's built-in transition utilities.
- Because there is **no keyboard traversal or DnD in the source**, "porting kibo-ui's Tree" only buys expand/collapse + click/Ctrl-click multi-select + icon rendering + indentation lines. The keyboard-reparenting requirement in the task's framing (§4 below) would have to be **built from scratch on top of the ported component regardless** — kibo-ui does not reduce that work at all. This substantially changes the cost-benefit: you'd be porting styled markup and then writing the actually-hard part (accessible keyboard tree semantics) yourself either way.
- Net estimate: porting the visual/structural shell is a **small-to-medium** job (one file, no Radix entanglement, straightforward Context state) — plausibly a few hours of token remapping and stripping the `@repo/shadcn-ui` workspace import. But it does **not** discharge the accessibility requirement in §4, which is the larger piece of work regardless of which base is chosen.

## 3. Alternatives

### react-complex-tree → headless-tree (same author, explicit successor)

- **react-complex-tree**: zero runtime dependencies, framework-agnostic styling (you provide all CSS — genuinely headless), natively implements WCAG 2.1 AA / ARIA tree semantics, built-in drag-and-drop reordering/reparenting "without extra packages", built-in multi-select and inline renaming [SANNSYNLIG — from a third-party technical write-up (marcotec.it, Dec 2025) and an npm-compare summary; not independently opened at a primary source within budget]. Reported gzip size ≈ 30 kB [SANNSYNLIG, same source].
- Its own author, Lukas Bach, has **publicly framed headless-tree as its successor**: "Headless-Tree, and the Future of React-Complex-Tree" (Medium, Lukas Bach) [DOK — title/URL confirmed via search, https://medium.com/@lukasbach/headless-tree-and-the-future-of-react-complex-tree-fc920700e82a; I did not open the full article]. That is a maintenance-status signal worth taking seriously: **new feature work is going to headless-tree, not react-complex-tree**, so choosing react-complex-tree today means choosing the library its own maintainer is stepping back from.
- **headless-tree** (`@headless-tree/core` + `@headless-tree/react`, headless-tree.lukasbach.com): fully headless, "definitive tree component for the Web." Confirmed features from its own docs [DOK — https://headless-tree.lukasbach.com/]: ordered drag-and-drop reparenting, extensive customizable hotkeys, typeahead search anywhere in the tree, item renaming, checkboxes, selection, and explicit compatibility with virtualization libraries for 100k+ items. It **automatically computes the full set of ARIA props per item** — `aria-level`, `aria-setsize`, `aria-posinset`, `aria-expanded` are explicitly named as auto-generated [DOK — via search-result quote sourced from the project's own docs/GitHub, matching the "definitive… for the Web" self-description]. As of the check (Aug 2026) the npm packages are at **Beta**, dated **17 May 2026**, with the maintainer stating general release "within two months" of that beta [SANNSYNLIG — npm registry metadata surfaced via search snippet, not opened directly]. ⚠️ **Flag: beta, not yet GA**, and I could not independently confirm a firm 1.0 date or verify it against npmjs.com directly within budget — treat the "within two months" line as the maintainer's stated intent at time of beta, not a confirmed release.
- Bundle size for headless-tree specifically: **[IKKE FUNNET — søkte ikke direkte etter bundlephobia-tall for @headless-tree/core innenfor budsjettet]**.

### react-arborist

- Virtualized (renders only visible rows — irrelevant at Humla's scale, see §5), supports drag-and-drop, expand/collapse, dynamic/async child loading. Described in secondary sources as "fast and virtualised by default but less flexible on the accessibility front" [SANNSYNLIG — npm-compare.com / blog summaries, not the library's own docs]. That "less accessible" characterisation is a secondary-source claim I could not verify against react-arborist's own documentation within budget — recorded as a gap, not a confirmed finding: **[IKKE FUNNET — søkte ikke direkte i react-arborist sin egen ARIA-dokumentasjon]**.
- Exact last-publish date and current maintenance cadence: **[IKKE FUNNET — søkte etter "react-arborist npm last published" men fikk ikke en konkret dato innenfor budsjettet]**. Treat maintenance status as unconfirmed rather than assuming either healthy or abandoned.
- Bundle size: not confirmed with a number; not found within budget.

### Ariakit / Base UI

- Neither ships a Tree primitive as of this check. Base UI (the MUI-maintained continuation of the Radix/Floating UI lineage, per its own positioning) has an **open, unresolved GitHub issue explicitly requesting one**: `mui/base-ui#3327`, "Add Tree component" [DOK — https://github.com/mui/base-ui/issues/3327, title/existence confirmed via search]. Search results describe Ariakit similarly as having only "active proposals" for a tree, not a shipped primitive [SANNSYNLIG].
- One derivative library, **ReUI**, was surfaced offering a tree component built *on top of* both the Radix and Base UI primitive stacks, claiming full WAI-ARIA tree semantics, keyboard nav, multi-select and async loading [SANNSYNLIG — https://reui.io/components/tree, not opened directly; this would itself be shadcn-registry-shaped and carry the same port-cost profile as kibo-ui, likely worse since it explicitly targets two primitive stacks at once]. Not investigated further given budget — flagged as a candidate worth a follow-up look if kibo-ui and headless-tree are both rejected.
- **On Radix specifically:** confirmed no tree primitive exists in Radix's own package set (matches the task's premise). One relevant secondary-source claim surfaced during this research and worth flagging even though unverified: that **Radix UI was acquired by WorkOS and its update cadence has slowed** for some components [SANNSYNLIG — surfaced in a search-result summary of a "shadcn/ui vs Base UI vs Radix" comparison piece; I did not independently verify this at Radix's own repo/changelog]. If true, it's a mild argument for treating Base UI (the other primitive layer, from the original Radix team, now under MUI) as the more actively maintained option to build a hand-rolled tree on going forward — but Humla's four existing wrappers (`Popover`/`Menu`/`Select`/`Combobox`) are already built on Radix, so switching primitive layers just for a tree would fragment the codebase's primitive strategy. This is a trade-off to weigh, not a settled recommendation.

### Hand-building directly on Radix primitives

Radix has no tree primitive, but it does export the piece that a tree's keyboard model actually needs: **`RovingFocusGroup`**, the same internal primitive Radix's own `Tabs` and `ToggleGroup` use to implement single-tab-stop, arrow-key-moves-focus behaviour [SANNSYNLIG — from training knowledge of Radix's package set, not re-verified against Radix's docs within this session's budget; recommend confirming the current export name/package before relying on it, as Radix's own pace of change is itself in question per the WorkOS note above]. A hand-build would combine:
- `RovingFocusGroup` (or a hand-rolled roving-tabindex `useReducer`) for the "one tab stop enters the tree, arrows move focus within it" behaviour the ARIA pattern requires,
- Radix's existing `Collapsible` primitive (already exportable from the same family) per node for expand/collapse state + `aria-expanded`,
- manually computed `role="tree"`/`role="treeitem"`, `aria-level`, `aria-selected`, `aria-expanded` attributes (none of Radix's primitives compute a tree's structural ARIA attributes automatically — that logic is exactly what headless-tree automates and what a hand-build would have to write itself),
- a custom Left/Right handler to collapse/expand and move to parent/first-child (not provided by any Radix piece),
- drag-and-drop, if wanted, via a separate library entirely (`@dnd-kit/core` is the current standard pairing for this kind of reparenting UI) since Radix has nothing here.

This is the most Humla-idiomatic option in spirit (stays on the existing primitive family, no new token vocabulary) but is also the most from-scratch: it reuses one low-level Radix piece and writes the entire tree-specific ARIA/keyboard contract by hand — realistically comparable in effort to writing a small headless tree library, not a thin wrapper.

## 4. Accessibility (WAI-ARIA tree pattern)

The reference is the W3C APG Tree View pattern (surfaced directly in search results: https://www.w3.org/WAI/ARIA/apg/patterns/treeview/ [DOK — URL confirmed, content not re-fetched since the pattern itself is stable/well-known and not in dispute]). It requires, at minimum: `role="tree"` on the container, `role="treeitem"` on nodes, `aria-expanded` on expandable nodes, `aria-level`/`aria-setsize`/`aria-posinset` (or reliance on DOM nesting, which flattened/virtualized trees can't do, hence needing the explicit ARIA props), roving `tabindex` (one tab stop for the whole tree, arrow keys move a virtual focus within it), Up/Down to move between visible rows, **Right to expand a closed node or move into its first child, Left to collapse an open node or move to its parent**, Home/End to jump to first/last row, and type-ahead to jump to a node by first character.

## 5. Virtualization — does it matter at this scale?

**No — plainly a non-issue.** Humla is a personal/small-team notes app; the folder list is user-authored organisational structure (per project docs: "flat folder list, per-note assignment"), realistically tens of folders, not hundreds, let alone the thousands or 100k+ items that virtualization exists to solve. React-arborist's virtualization and headless-tree's "100k+ items" compatibility are both irrelevant selling points for this use case — they solve a problem Humla doesn't have. Do not let virtualization support influence this decision; if anything, a library whose main pitch is virtualization (react-arborist) is solving for a scale mismatch with this app, which is a mild signal that it's the wrong tool for the job rather than a neutral extra feature.

The one place scale *could* matter is if the sidebar tree needs to also show notes nested under folders (not just folders), which could run into the low hundreds for a heavy user over years — still nowhere near virtualization territory, and irrelevant to the component choice either way.

## Konklusjon og anbefaling

**The decision this serves:** how to render/interact with a nested folder tree in Humla's sidebar for #162, given the hard constraint of no shadcn/CVA and the existing Radix-wrapper convention, and given that keyboard reparenting is a real requirement independent of whether drag-and-drop ships.

**Recommendation: do not port kibo-ui's Tree.** It looked, from the docs page alone, like a plausible shortcut ("shadcn-registry, just port the source"), but the actual source (confirmed by direct inspection) has **no ARIA roles, no arrow-key navigation, and no drag-and-drop** — it is styled, animated, indented `<div>`s with click-to-select. Every requirement that actually matters for #162 (keyboard reparenting, and DnD if it ships) is entirely unaddressed by kibo-ui; porting it only buys expand/collapse animation and icon rendering, at the cost of (a) rewriting every shadcn-token class name against Humla's own vocabulary and (b) adding `motion` as a new runtime dependency for an animation Humla could do in CSS. The port is small, but so is what it delivers — and it delivers essentially none of the hard part.

**Recommendation: evaluate `headless-tree` as the leading candidate**, with eyes open about it being Beta. It is the only option reviewed whose own documentation explicitly states it computes the structural ARIA attributes (`aria-level`, `aria-setsize`, `aria-posinset`, `aria-expanded`) automatically, and it explicitly ships ordered drag-and-drop reparenting and a comprehensive hotkey system including typeahead — the exact three things Humla actually needs (accessible keyboard tree semantics, optional DnD, no styling assumptions to fight). Because it's headless, Humla writes its own markup and Tailwind classes against its own tokens from day one — no port, no token translation, and it slots naturally next to the existing `Popover`/`Menu`/`Select`/`Combobox` wrapper pattern as a fifth in-house wrapper (`Tree`), consistent with how the codebase has consolidated every other anchored/structured UI element. The main trade-off: **Beta status** — no confirmed GA date, no long production track record, and I did not hands-on test it. If that risk is unacceptable for a #162 timeline, the fallback is **react-complex-tree** (its accessibility/DnD claims are well-attested in secondary sources even though not independently verified here) with the explicit understanding that you'd be adopting a library its own author has signalled is heading toward maintenance-mode in favour of headless-tree.

**Do not hand-build from scratch on Radix as the first move.** It's the most idiomatic fit with Humla's existing primitive convention, but per §3 it means writing the entire ARIA/keyboard contract in-house with no upstream test coverage — realistically as much work as headless-tree already did, and Humla would own all of it going forward. Worth reconsidering only if headless-tree's Beta risk proves unacceptable *and* react-complex-tree's slowing-maintenance signal is also judged disqualifying.

**Virtualization is a non-factor** for this decision — Humla's folder counts are nowhere near the scale where it matters, so don't let react-arborist's virtualization pitch or headless-tree's "100k+ items" claim sway the choice either way.
